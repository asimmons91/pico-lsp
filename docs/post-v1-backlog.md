## 1. Homebrew and Mason packaging

Complete the two install channels deferred from M6.

Requirements:

- Publish a Homebrew tap formula generated by goreleaser or maintained from a
  small template.
- Publish a Mason registry package whose source is the GitHub release assets.
- Test installation and `pico-lsp --version` on clean environments.
- Document upgrade/uninstall paths.
- Keep the release workflow able to skip these publishers if credentials or
  registry access are unavailable.

## 2. VS Code Marketplace and Open VSX publishing

Publish the M15 client to the VS Code Marketplace and Open VSX. M15 ships the
extension as a GitHub release VSIX; this follow-up makes it discoverable and
one-click installable.

Requirements:

- Register and verify `asimmons91` as the publisher in both registries.
- Keep Marketplace and Open VSX publishers independently retryable.
- Publish from the release workflow using repository secrets, with a documented
  manual fallback.
- Include the extension README, icon, LICENSE, CHANGELOG, repository links,
  categories, and keywords in both listings.
- Publish only VSIXs that passed the M15 CI and release checks.
- Test installation from both registries on all supported local desktop
  platforms.
- Document install, upgrade, and uninstall paths for each registry.

## 3. Zed extension

Provide PICO-8 support in Zed.

Requirements:

- Thin extension that launches the release binary.
- Language configuration for `.p8` and, where supported, cart-owned `.lua`.
- Optional tree-sitter grammar for highlighting.
- Binary architecture detection and clear installation errors.
- Document manual binary configuration.

## 4. API version selection

Support additional PICO-8 API versions.

Requirements:

- Add versioned built-in stub sets.
- Make `pico8.apiVersion` select the active set.
- Keep 0.2.7 as the default for existing configurations.
- Report unsupported versions with the existing fallback warning.
- Document differences that affect diagnostics and completion.

## Cross-cutting requirements

- No regressions in v1, v1.1, v1.2, or v1.3 behavior or performance budgets.
- Every feature is additive or explicitly opt-in.
- Update the roadmap, README, configuration docs, diagnostic reference, and
  changelog.
- Maintain the editor-agnostic server contract.
- Keep the existing testing standards: unit, golden, LSP e2e, corpus, fuzz where
  applicable, and release smoke tests.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Packaging credentials or registry lag | Ship GitHub binaries first; make publishers independently retryable. |
| Client/packaging drift | Shared release assets, thin clients, platform smoke tests. |
| API-version stub drift | Versioned stub fixtures and explicit fallback diagnostics. |
| Scope creep | Backlog is prioritized; only promoted items become milestones. |
